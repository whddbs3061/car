# 계획: 카메라 차선 인식 — 학습 라벨 파이프라인 다음 단계

## Context

지금까지는 `GenerateLabels.py`가 HD맵을 카메라에 투영해 8클래스 픽셀 라벨을 만드는 데까지 완성돼 있고(초점거리·yaw·자세 보정 다 끝남), 이걸로 실제 학습을 시작하기 전에 오늘 세 가지를 정리했다:

1. **프레임 동기화** — 직진/정지에서는 라벨이 정확한데 조향·제동 중엔 어긋나는 문제 (원인 미확정, 진단 방법만 정리됨)
2. **학습 입출력 설계** — 클래스 수, 차선 ID를 어떻게 부여할지, 픽셀/폴리라인 중 뭘 출력으로 쓸지
3. **데이터 수집 규모** — `drive6` recording이 2026 국토교통부 대회 코스(`2026_molit_comp_global_path.txt`, 총 2,184.6m 폐루프) 한 바퀴와 거의 정확히 일치(주행거리 2,178.6m)한다는 걸 확인했고, 몇 바퀴/몇 장이 필요한지 실측 기반으로 추정함
4. **모델 아키텍처·배포 환경** — PolyLaneNet(`PolyRegression`) 기반으로 정하고 ONNX export/구조 호환성 검증까지 실제로 돌려서 통과시켰다. 그 과정에서 실제 배포가 RTX 4090 데스크톱이라는 게 확인되면서, 그동안 아키텍처를 옥죄던 cv2.dnn/CPU 제약이 사실상 풀렸다.

이 문서는 그 논의를 다음 실행 단계로 정리한 것이다.

## 오늘 확정된 결정 사항

- **클래스**: `GenerateLabels.py`는 지금처럼 8클래스 그대로 생성(정보 손실 없는 원본 유지). 1차 학습은 클래스 리맵으로 **5종(배경/백색실선/백색점선/황색/정지선)**만 사용.
- **차선 ID는 라벨 생성 시점에서 부여**: `LaneEgoSelect.py`가 노이즈 있는 픽셀에서 겪었던 그룹핑 실패(폭 167~1155px로 벌어짐, 좌우 교차 등, [CLAUDE.md:115-120](car/src/perception/camera_perception/CLAUDE.md#L115-L120))는 `GenerateLabels.py`에서는 재현되지 않는다 — HD맵 원본 + 정확한 자차 위치가 있으므로 각 경계의 자차 기준 횡방향 오프셋을 노이즈 없이 계산할 수 있다.
- **차선 ID 범위는 ego 좌우 2개로 한정하지 않는다**: 화면에 보이는 모든 경계를 자차 기준 횡방향 오프셋(ego 좌표계 y, `to_ego`가 이미 계산)으로 정렬해 상대 순번(예: 가장 가까운 좌측=ego_left, 그 다음=left_2 … 우측도 동일)을 매긴다. 이렇게 하면 인접 차로 경계까지 식별 가능해지고, "어느 게 내 차로냐"뿐 아니라 "이 선들이 서로 다른 선이다"라는 정보 자체가 라벨에 들어간다.
- **출력은 두 종류를 같이 생성**:
  - (a) 기존 방식대로 **픽셀 래스터** (5클래스 마스크) — 팀원이 다른 아키텍처를 시도할 때 범용으로 재사용
  - (b) **신규: 구조화(vector) 라벨** — 프레임별로 각 경계의 `차선 ID(상대 순번)`, `클래스`, `실선/점선 여부`, `이미지좌표 폴리라인 점열`을 JSON으로 저장. `render_frame_labels`에서 `cv2.fillPoly`로 래스터에 굽기 **전에** 이미 계산되는 `to_ego`/`cam.project` 좌표를 그대로 내보내면 된다.
  - 주의: 픽셀 래스터만으로는 나중에 차선 ID를 복원할 수 없다(같은 클래스의 여러 경계가 한 캔버스에 섞여 그려짐) — 그래서 (b)를 별도로 만들어야 함.
- **라벨 품질과 모델 정확도는 별개**: 차선 ID 라벨 자체는 HD맵 기반이라 노이즈가 없지만, 학습된 모델이 카메라만으로 항상 정확히 맞힌다는 보장은 아니다 — 특히 차로 변경처럼 경계 자체가 모호한 프레임에서는 모델도 헷갈릴 수 있다. 실제 추론 정확도는 결국 학습 데이터가 다양한 상황(차로 수 변화, 차로 변경 등)을 얼마나 커버하느냐에 달려있다.
- **[중요, 2026-08-26 갱신] 실제 배포 타깃은 RTX 4090 데스크톱이지 CPU가 아니다.** `CLAUDE.md`의 "cv2.dnn을 쓴다"는 결정은 사용자가 예전에 GPU 없는 개인 노트북에서 돌려보려던 개인적 이유였고, **대회 규정상 강제되는 것도 아니다.** 즉 지금까지 아키텍처를 옥죄던 "cv2.dnn 호환 연산만 사용" 제약은 최종 모델에는 더 이상 필수가 아니다(로컬 테스트용으로 선택적으로 유지하는 것은 가능). 학습은 Colab/RunPod 같은 클라우드 GPU에서 진행 예정 — 로컬 `vision_env`는 CPU 전용 빌드(`torch.cuda.is_available()=False`, opencv도 CUDA 미포함)라 학습에는 못 쓰고, 구조 검증(ONNX export 등) 용도로만 유효.
- **카메라 해상도**: 시뮬레이터/대회 카메라 원본 해상도는 **1280x720**이며 대회 주최측이 고정한 값이다([RecordDrive.py:13-15](car/src/perception/camera_perception/RecordDrive.py#L13-L15)). 640x360은 기존 YOLOP onnx 모델이 요구했던 입력 크기였을 뿐 하드웨어 제약이 아니었음. RTX 4090 배포로 바뀌면서 CPU 기준 속도 트레이드오프(640x360 4.71FPS vs 1280x720 1.39FPS, resnet34/cv2.dnn 실측)는 최종 배포에는 크게 문제되지 않을 가능성이 높다 — 기본값은 **1280x720 그대로 사용**하는 쪽으로 기울되, 실제 GPU(Colab 등)에서 재벤치마크해 확정한다.
  - **장애물 탐지 모델에도 같은 트레이드오프가 별도로 걸림**: 차선 모델과 독립인 장애물 탐지(동적/정적/차량 3종) 쪽은 해상도를 낮추면 원거리 소형 물체(특히 가장 먼저 반응해야 하는 동적 장애물) 탐지율이 떨어지고, 동적/정적 구분에 쓰이는 프레임 간 미세 움직임 단서도 약해진다. 두 모델이 독립 프로세스라 GPU 예산도 각자 판단해야 함.
- **베이스 모델은 새로 설계**: 기존 `lane_segmentation.onnx`(YOLOP 2채널)는 재사용 안 함. 출력은 차선 ID별 다항식 계수(연속 곡선) + 실선/점선 같은 이산 속성으로 구성. `cv2.dnn` 제약이 풀렸으므로 백본 선택 폭도 넓어짐(EfficientNet의 Swish 활성화 등 cv2.dnn 호환성 걱정 안 해도 됨) — 다만 ResNet34로 이미 구조 검증이 끝났으니 굳이 바꿀 필요는 없음.
  - **[검증됨, 2026-08-26]** PolyLaneNet(`lucastabelini/PolyLaneNet`)의 `PolyRegression`(backbone=resnet34, 5슬롯×7 + extra 5슬롯×3클래스, opset12)을 랜덤 가중치로 export → `cv2.dnn.readNet` 로드 → `forward()`까지 전부 성공 (CPU 환경에서의 구조적 호환성 검증 — GPU 배포로 방향이 바뀌었어도 이 결과 자체는 여전히 유효/유용함, "적어도 CPU에서도 돌아간다"는 하한선 확인). `getUnconnectedOutLayersNames()`로 `('output','extra_output')` 두 출력 모두 정상 수신(YOLOP의 da/ll과 같은 패턴).
  - **추론 배포**: cv2.dnn 대신 `onnxruntime-gpu`(CUDA EP, pip 설치로 간단) 또는 학습에 쓴 PyTorch를 그대로 CUDA로 추론에 쓰는 방안을 우선 고려. 학습이 Colab/RunPod의 PyTorch라 ONNX 변환 단계 자체를 생략하고 PyTorch 직접 추론이 제일 단순하고 리스크가 적음 — RTX 4090 여유를 보고 필요하면 나중에 onnxruntime/TensorRT로 최적화.
- **점선 표현 단순화**: 대시 on/off 위상을 기하학적으로 재현할 필요 없음 — 연속 곡선 + `broken` 이산 속성이면 충분.
- **손실/학습**: 가중 CE, 우선 소규모 데이터로 파이프라인 검증 후 전체로 확장.
- **train/val 분할**: 프레임 랜덤 분할 금지(연속 프레임 유사도로 leakage) — recording 단위 또는 충분히 떨어진 구간 단위로 분할.
- **데이터 규모**: 기본 `--png-interval-m 4.0` 기준 한 바퀴(2,180m) ≈ 545장. 목표 3,000~5,000장 맞추려면 약 5~9바퀴(속도/조향 프로파일을 바꿔가며) + 정지선 구간은 추가 통과 필요.
- **오브젝트(다른 차량 등) 가려짐 ignore 마스크는 이번 계획에서 보류**: `drive6`(2,772프레임) 전수 확인 결과 `objects`가 기록된 프레임이 **0개**라 지금은 만들어도 눈으로 검증할 방법이 없다. 실제로 다른 차량이 잡힌 녹화본이 생기면 그때 설계·구현한다. (구현 스케치는 아래 "보류 항목" 참고)

## 실행 계획

### 0단계 — 검증용 데이터 로컬로 가져오기

`recordings/test1`(5프레임: `000000/000105/000123/000141/000214`, `perception/camera-lane` 브랜치에 존재, 이전 `label_check/` 결과 포함)을 로컬 작업 트리로 가져온다.

```
git checkout origin/perception/camera-lane -- src/perception/camera_perception/recordings/test1
```

기존 작업 중인 파일들(`GenerateLabels.py` 등 이미 수정된 상태)엔 영향 없음 — 새 경로만 추가됨.

### 1단계 — `GenerateLabels.py`: 5클래스 리맵 옵션 추가

`LANE_TYPE_TO_CLASS`/`CLASS_*`는 그대로 두고, 최종 마스크를 저장/출력할 때만 `{배경, 백색실선, 백색점선, 황색, 정지선}`으로 합치는 리맵 레이어 추가 (예: `--train-classes lane5` 같은 옵션). 8클래스 내부 표현은 유지.

### 2단계 — `GenerateLabels.py`: 구조화(vector) 라벨 출력 추가 (차선 ID 포함)

`render_frame_labels` 내부, 경계별로 `to_ego` 좌표가 계산된 시점에서:
- 각 경계의 자차 기준 횡방향 오프셋(ego 좌표계 y값, 경계에서 자차와 가장 가까운 지점 기준)을 구해 좌/우로 정렬
- 정렬 순서대로 상대 차선 ID 부여 (예: `ego_left`/`ego_right`가 0번째, 바깥쪽으로 `left_2`, `right_2` …)
- 프레임별 JSON으로 `{idx, boundaries: [{lane_id, cls, broken, points_uv}, ...]}` 저장

### 3단계 — `recordings/test1` 5장으로 검증

- 5클래스 래스터가 기존 `label_check/frame_*.png`(구버전, 8클래스 오버레이)와 비교했을 때 위치가 여전히 잘 맞는지 육안 확인 (좌표계/투영 로직은 안 건드렸으므로 달라지면 안 됨)
- 새 구조화 라벨의 차선 ID가 실제 화면 속 차선 순서와 맞는지(왼쪽에서 오른쪽으로 순서가 맞는지, ego_left/ego_right가 실제 자차 좌우인지) 5장 전부 육안 검증
- 통과 기준: 5장 모두에서 차선 ID 배정이 직관과 일치하고, 5클래스 리맵이 원본 8클래스 대비 정보 손실만 있고 오류는 없을 것

### 4단계 — (3단계 통과 후) 본 녹화 계획 확정

이번 계획에서는 실행하지 않고, 3단계 결과를 보고 다음을 확정한다:
- `RecordDrive.py --format both --png-interval-m <값>`으로 몇 바퀴 돌지 (기본안: 2~3m 간격, 5~9바퀴 + 정지선 구간 추가 통과)
- 재녹화 시 조향/제동 다양성을 의도적으로 섞어서 프레임 동기화 진단용 데이터도 같이 확보
- 이때 다른 차량(트래픽)을 시뮬레이터에 배치해서 `objects`가 실제로 기록되게 하면, 아래 "보류 항목"(오브젝트 가려짐)을 검증할 데이터도 같이 확보됨

### 5단계 — 라벨 포맷 스펙 문서화 (팀원 공유용)

5클래스 정의, 차선 ID 정의, 구조화 라벨 JSON 스키마를 정리해 팀원에게 전달 — "어떤 데이터가 필요한지 모른다"는 문제의 실질적 해결책. `camera_perception/CLAUDE.md`에 섹션 추가하는 형태를 권장.

### 6단계 — PolyRegression 학습 타깃 변환 스크립트

2단계의 구조화 JSON을 PolyLaneNet `PolyRegression`의 출력 형식(5슬롯×7 + extra 5슬롯×3클래스, 아키텍처 검증 완료)에 맞는 학습 타깃으로 변환하는 스크립트. 학습 파이프라인(Colab/RunPod) 쪽 작업이라 실제 착수는 본 녹화 데이터가 쌓인 이후:
- `lane_id` → 고정 슬롯 인덱스(0~4) 매핑
- 슬롯에 해당 `lane_id`가 있으면 `conf=1`, 없으면 `conf=0`(값은 loss에서 무시)
- `points_uv`의 y 최소/최대 → `lower_y`/`upper_y`
- `points_uv`에 `np.polyfit(y, x, deg=3)` → `a,b,c,d`
- `cls`(백색실선/백색점선/황색) → extra_outputs 3-way 라벨 (`broken`은 `cls`에 이미 포함되므로 별도 불필요)
- **정지선은 이 회귀 head로 표현 불가** — PolyRegression은 진행방향 곡선(`x=f(y)`) 전용이라 가로선인 정지선엔 안 맞음. 같은 백본을 공유하는 별도의 작은 세그멘테이션/2점-회귀 head 필요 (5클래스 래스터의 정지선 채널에서 라벨 파생)

## 보류 항목 — 오브젝트 가려짐 마스크 (실제 오브젝트 녹화본 확보 후 착수)

지금 당장 구현하지 않지만, 나중에 착수할 때를 위한 설계 방향만 남겨둔다:
- `objects`(pose_x/y/z, heading, size_x/y/z)로 3D 박스를 만들고, 기존 `to_ego` → `cam.to_camera`/`project` → `clip_near`를 그대로 재사용해 이미지에 투영
- **[확인됨] `objType`은 동적장애물/정적장애물/차량 3종.** 가려짐 마스크 자체는 종류 구분 없이 모든 오브젝트를 후보로 처리해도 되지만, 이 3분류는 별도의 카메라 기반 장애물 탐지 모델(차선 모델과 별개, `samples/animals`·`samples/bikes`·`samples/boxconedrum`에 관련 데이터 존재)의 출력 클래스와 연결된다 — 아키텍처가 차선 모델과 백본을 공유하는지는 미결정 (해상도/속도 예산에 영향)
- 투영된 영역은 보닛 마스크와 같은 방식으로 마지막에 `CLASS_IGNORE`로 덮음 — "불확실하면 ignore" 기존 원칙과 동일
- `heading` 각도 관례(ego yaw처럼 ENU 반시계인지)는 검증된 적이 없어 실제 녹화본이 생기면 눈으로 확인 필요 (ego yaw/roll/pitch를 확정했던 것과 같은 방식)

## 별도 트랙 — 프레임 동기화 진단 (병행 가능, 우선순위 낮음)

1단계~3단계와 독립적으로 진행 가능한 진단 작업. **가드레일처럼 지도에 없는 물체가 차선으로 잘못 라벨링될 위험도 근본 원인이 여기 있다** — `GenerateLabels.py`는 가드레일이라는 개념 자체를 몰라서(HD맵에 없음) 가드레일을 차선으로 그릴 방법이 없다. 진짜 위험은 "실제 차선 라벨이 계산 오차로 밀려서 하필 가드레일 위에 겹쳐 그려지는 것"이고, 이 오차는 커브·조향 중에 커진다는 게 이미 문서화돼 있다(`GenerateLabels.py`: pitch 2도 오차 → 10m에서 2.9m 어긋남). 즉 아래 진단·조향 필터가 이 문제의 실질적 해결책이며, 데이터가 생기면 커브 구간 프레임 몇 장을 골라 가드레일 근처로 라벨이 새는지 눈으로 확인하는 게 가장 빠른 검증이다.

- 브레이크 임계값(`BRAKE_SKIP_THRESHOLD=0.05`) 이하에서도 어긋남이 보이는지 확인
- 조향 구간에서 `t_cam`에 임의의 상수 오프셋을 걸어 딱 맞는 delta가 있는지 확인 (있으면 카메라-상태 시각 자체의 고정 지연 문제)
- `cam_sec/nsec` vs `status_sec/nsec` 직접 비교 ([RecordDrive.py:23-24](car/src/perception/camera_perception/RecordDrive.py#L23-L24) 주석에 이미 제안돼 있던 방법)
- 조향에는 지금 필터가 없으므로 `ang_vel_z`/`steer` 기준 스킵 필터 추가 여부 결정 — 가드레일 오라벨링 방지에도 가장 직접적인 대응

### 참고 — ROI 기반 ignore 마스크 (거리 기반 클러터 대응, 선택적, 낮은 우선순위)

위 가드레일 문제와는 원인이 다른, "너무 멀어서 지도에 없는 지형지물이 화면에 많이 보이는" 경우에 한해 별도로 고려 가능. `LaneEgoSelect.py`의 `limit_region`(사다리꼴 ROI, bottom/top/height=1.00/0.80/0.65, [CLAUDE.md:99-102](car/src/perception/camera_perception/CLAUDE.md#L99-L102))과 같은 형태를 학습 라벨 생성 단계에 적용해, ROI 밖 픽셀을 `CLASS_IGNORE`로 처리하는 방식 — 입력 이미지는 자르지 않고 손실 계산에서만 제외한다(보닛·애매한 횡단보도(544)에 이미 쓰는 "불확실하면 ignore" 패턴과 동일).
- **가드레일처럼 거리와 무관하게 도로 옆에 계속 있는 물체는 이 방법으로 못 거른다** — 사다리꼴 안쪽에도 들어올 수 있어서, 그 경우는 위 프레임 동기화 트랙이 실질적 해법이다.
- `MAX_RANGE`(현재 80m)를 좁히는 것도 거리 기반 대안이지만, 이미 한 번 30m로 줄였다가 다른 이유(원거리+비스듬한 시야각 왜곡)로 80m로 되돌린 이력이 있다([GenerateLabels.py:144-152](car/src/perception/camera_perception/GenerateLabels.py#L144-L152)) — 다시 건드리기 전에 이 이력을 참고할 것.

## 검증 방법

- 1~2단계 코드 변경 후 `recordings/test1`(5장)으로 `GenerateLabels.py` 실행 → 래스터 PNG + 구조화 JSON 육안/수치 확인 (3단계 기준과 동일)
- 문제 없으면 이 결과를 캡처해두고 4단계(본 녹화) 착수 여부를 사용자와 다시 확인
- 6단계(PolyRegression 타깃 변환)는 본 녹화 데이터가 쌓인 뒤 착수 — 검증은 변환된 타깃으로 실제 소량 학습(수십 epoch)을 돌려 loss가 정상적으로 떨어지는지, decode한 다항식이 원본 이미지 위에서 차선과 대략 맞는지로 확인
- 모델 구조 자체의 export/로드 가능성은 이미 검증 완료(2026-08-26, CPU/cv2.dnn 기준) — GPU/PyTorch 직접 추론으로 방향이 바뀌었지만 재검증 불필요, 오히려 변환 단계가 없어져 리스크가 줄어든 방향
