## 1. 왜 이걸 하는가

`src/perception/camera_perception/LaneCandidates.py` 는 이진 차선 마스크에서
실선/점선/정지선/유도선을 **후처리로** 판별한다. 한계가 측정으로 확인됐다:

- `fill_ratio` 는 연결 성분 1개짜리 후보에서 **정의상 정확히 1.000** (262개 전부) → 점선 판정 0개
- 마스크 직접 탐침 + 프레임 간 추적으로 개선했지만, 화면 안쪽 후보의 트랙 판정 커버리지가 21%에 그침
- 교차로에서 `trk=0/4` — 판정 근거가 아예 없어 유도선이 전부 실선으로 표시됨
- 급커브에서 조각이 최소 크기 필터에 걸려 차선이 통째로 사라짐

차선 **존재** 검출은 CNN이 잘 하므로, 종류 판별까지 모델 출력으로 끌어올린다.

**결정적 발견**: `lane_boundary_set.json` 에 정답 라벨이 이미 다 들어 있다.
수작업 라벨링 없이 학습 데이터를 자동 생성할 수 있다.

### 대회 조건 (설계를 좌우함)
- 코스 **고정** (`R_KR_PR_K-city_2025` — 보유 MGeo 와 동일 맵)
- 시나리오만 변동: 동적장애물 / 차량 끼어들기 / 정적장애물 / 날씨 / GPS음영 / 고속도로 차선변경 중 **2개 조합**이 히든미션
- → 처음 보는 도로로의 일반화는 불필요. **K-City 과적합이 목표.**

### 기존 공개 모델을 안 쓰는 이유
실선/점선 라벨이 있는 데이터셋은 존재하지만(BDD100K `laneStyle`, OpenLane 14종,
VIL-100, SemSeg-Lanes 10종), **받아서 바로 쓸 ONNX 가 없다.** 있어도 실제 도로
학습이라 MORAI 합성 영상과 도메인이 다르고, cv2.dnn 이 최신 아키텍처의 op 를
못 읽는다. 자체 학습이 더 빠르고 확실하다.

### 설계 원칙 — 지도에 있는 노면 도색은 **전부** 라벨링한다

배경으로 남은 도색은 모델에게 "이만한 흰 도색은 아무것도 아니다"라고 가르치고,
그 억제가 생김새가 비슷한 클래스(정지선·`zone`·안전지대 빗금)로 새어나간다.
주차구역에서 실제로 확인된 문제다.

그래서 재 export 이후에는 **지도에 있는 노면 도색을 하나도 빠뜨리지 않고**
라벨에 넣는다. 종류를 확정할 수 없는 것은 배경이 아니라 **`unknown` 클래스**로 둔다.

#### `unknown` 과 `ignore` 는 정반대다 — 섞지 말 것

| 상태 | 처리 | 손실 | 근거 |
|---|---|---|---|
| 도색인 게 확실, **종류를 모름** | **`unknown`** | 포함 | 배경으로 두면 "이 도색은 무시하라"고 배운다 |
| **도색인지조차 불확실**, 또는 가려짐 | **`ignore`** | 제외 | 어느 쪽으로 단정해도 틀릴 수 있다 |
| 도색이 확실히 없음 | 배경 | 포함 | 맞는 라벨이다 |

가려짐(보닛·앞차)은 두 번째에 속한다. `singlecrosswalk_set` 의 `sign_type 544`
(13개)도 두 번째다 — 영상에 얹어 보니 대부분 맨 아스팔트 위에 놓여서, `unknown`
으로 두면 없는 도색을 있다고 가르치게 된다.

`ignore` 를 도색에 쓰면 모델이 그 자리를 아예 보지 않는다. `unknown` 이면
"도색은 있다"까지 배우고, 후처리가 그걸 받아 판단할 수 있다. 나중에 정체를
알게 되면 그때 별도 클래스로 승격하면 된다.

**`unknown` 이 클래스로 성립하는 이유**: 노면 도색은 종류가 달라도 "아스팔트 위
밝은 고대비 영역"이라는 **공통 외형**을 갖는다. 반면 합류차선은 시각적 특징이
없어서(일반 흰 점선과 동일) 클래스로 만들면 안 된다 — 같은 픽셀에 다른 라벨을
주게 되어 다른 클래스까지 오염된다. 이 둘의 차이가 클래스 추가 여부의 기준이다.

### ✅ 초점거리 확정 — FOV 90 은 **수평** (Phase 1 실측)

`GenerateLabels.py` 로 두 가설을 나란히 렌더링해 확정했다. 수평 가설에서 황색
오버레이가 중앙선에, 파란 점선이 흰 점선에 정확히 얹힌다. 수직은 눈에 띄게 어긋난다.

```
원본 1280×720, FOV 90 수평 → f = 640 (정사각 픽셀)
640×480 저장 시 (비등방)   → fx = 640*(640/1280) = 320
                             fy = 640*(480/720)  = 426.7
```

**두 축을 같은 값으로 두면 세로가 33% 틀린다.** 구조는 맞아 보이는데 정합만
나쁜, 가장 찾기 어려운 오차다. 처음에 이걸로 헤맸다.

> **수치 지표로는 두 가설을 구분할 수 없다.** 둘 다 `fy/fx = 1.333` 으로 같아서
> 지면 역투영의 가로 좌표 `X ∝ fy/fx` 가 동일하다 — 차로폭이든 가로오차든 같은
> 숫자가 나온다. 겹침 비율 지표는 더 나쁘다: 틀린 가설이 투영을 소실점 쪽으로
> 압축시키는데 거기가 검출이 조밀한 곳이라 **압축을 보상해버려 틀린 쪽이 이긴다.**
> 구분하려면 지도의 3D 좌표를 투영해 픽셀 위치를 보는 수밖에 없다 = 오버레이.

### 데이터에서 확정한 좌표 관례 (추측하지 말 것)

1. `yaw` 는 ENU East 기준 **반시계**. drive6 에서 실제 이동방향 `atan2(dy,dx)` 와
   yaw 차이가 −1.3~−1.7° 로 일관되게 작다.
2. 자차 좌표계는 **x 전방 / y 좌측 / z 상방** (`cam_set` 좌측 카메라가 `y=+0.65`).
3. **노면 높이를 상수로 두지 말 것.** 맵 표고차가 10.29m (27.14~37.43m) 다.
   `meta.jsonl` 의 `link_id` 로 링크를 찾아 자차에 가장 가까운 점의 z 를 쓴다
   (drive6 2772프레임 전부 조회 성공, 자차와 0.2~2.3m).
4. 폴리라인 점 간격이 중앙값 1.97m, 최대 36.1m — **재보간 없이는 대시(3m)를
   표현할 수 없다.**

### Phase 1 에서 잡은 버그 5개

1. **`fx = fy` 가정** → 축별 배율 분리
2. **중앙선 겹선** — 지도는 겹선을 *같은 자리의 레코드 2개*로 표현한다 (501 의
   62%). 그대로 그리면 덧칠만 되어 실제 0.4m 폭이 0.15m 로 나온다 → 134쌍을
   `(폭+간격)/2` 만큼 좌우로 밀어 그린다
3. **복합선 두 쪽이 둘 다 실선 클래스** — `'solid broken'`(type 506, 9개)에서
   `cls` 를 `lane_type` 으로 정해 두 쪽에 물렸다. **"한쪽에서만 넘어올 수 있다"는
   정보가 라벨에서 통째로 사라진다** — 고속도로 진입 차선변경 판단의 근거가 바로
   이것이다. 각 쪽의 `shape` 에서 클래스를 정하도록 수정
4. **근평면 클리핑 없음** — 꼭짓점 하나라도 카메라 뒤면 폴리곤을 버려서 *자차가
   올라선 횡단보도*가 통째로 누락됐다
5. **보닛 위에 라벨** — 지면 폴리곤이 후드까지 칠했다. `da` 출력 평균으로 자동
   검출(y=387 아래, 화면의 13.4%)해 ignore 처리.
   부수 발견: 기존 후처리의 `ANCHOR_Y=430` 이 **보닛 안쪽**이었다

### ⚠ 남은 문제: 지도-도색 가로 편차 ~0.3m

황색 중앙선을 색으로 뽑아 라벨과 비교한 결과, **거리와 무관한** 가로 편차가 있다
(4.4m 에서 −0.28m, 14.6m 에서 −0.39m). 거리 비례가 아니므로 초점거리 문제가 아니고,
겹선 처리를 꺼도 그대로다(−0.266 → −0.307).

- 지도 정합 편차는 **아니다** — `lat = -Dx·sin(yaw) + Dy·cos(yaw)` 모델의 설명력이
  1% 뿐이고, 주행 방향이 180° 바뀌어도 부호가 안 뒤집힌다
- 자차 기준 오차로 보이나 **산포(0.547m)가 편차(0.35m)보다 커서** drive6 로는 확정 불가
- → **재녹화 후 다시 측정한다.** 라벨 생성기에 녹화본별 가로 보정값 자리를 만든다

### 해상도와 투영의 관계 (문제 없음)

1280×720 과 640×360 은 **등방 0.5× 관계**라 내부행렬만 절반으로 줄이면 수학적으로
완전히 동일하다. 어느 해상도에서 투영하든 결과가 같다.
```
1280×720 : fx = fy = F,     cx = 640, cy = 360
640×360  : fx = fy = F/2,   cx = 320, cy = 180     (F 는 위에서 확정)
(참고) 640×480 : fx ≠ fy 로 비등방 — 쓰지 않는다
```
**라벨 생성과 추론 모두 640×360 행렬을 쓴다.** 16:9 → 16:9 라 종횡비가 보존된다.

### ⚠ 포트는 1101 (cam_set.json 의 9291 아님)

`cam_set.json` 의 `udpConfig` 에는 전방 카메라가 **9291** 로 적혀 있지만, 실제
대회 설정에서는 **1101** 로 변경되었다. `RecordDrive.py` 기본값이 1101 이므로
포트는 그대로 두면 된다. **연구실에서 시뮬레이터 Network Settings 로 한 번 확인할 것.**

### ⚠ 남은 미지수: drive6 의 원본 해상도

`RecordDrive.py` 가 `cv2.resize(image, FRAME_SIZE)` 로 줄여 저장해서 `drive.mp4` 는
640×480 이다. 센서가 1280×720(16:9) 이었다면 4:3 으로 줄이는 과정이 비등방이라
`fx != fy` 가 되고, 애초에 640×480 으로 출력했다면 `fx == fy` 다.

- 현재 라벨 생성기는 **1280×720 원본 가정**으로 fx=320, fy=426.7 을 쓴다
- 오버레이 정합은 이 가정에서 잘 맞는다
- → **재녹화 시 축소 저장을 없애면 이 미지수가 사라진다.** 원본 해상도로 저장한다.

### Phase 1 — 라벨 생성 파이프라인

새 파일: `src/perception/camera_perception/GenerateLabels.py`

```
meta.jsonl(자차 pose) + lane_boundary_set.json(지도)
```

- **점선은 `dash_interval` 로 실제 대시/간격을 끊어서 그린다.** 통으로 그리면

### Phase 3 — 모델과 학습

#### 입출력 규격

**입력 텐서는 그대로.** ONNX 입력은 `(1, 3, 360, 640)` 고정이고 `blobFromImage` 가
무엇을 주든 640×360 으로 줄인다. 카메라 해상도는 모델이 신경 쓰지 않는다.
```
"images": (1, 3, 360, 640) float32
전처리:  cv2.dnn.blobFromImage(img, scalefactor=1/255, size=(640,360), swapRB=True)
```

**리사이즈 체인은 정리한다.** 1280×720 입력은 오히려 지금보다 깨끗하다:
```
지금   1280×720 → resize(640,480) [가로0.5 세로0.667, 4:3]
                → blobFromImage(640,360) [세로0.75]        = 리샘플링 2회, 비등방 중간단계
바꾼뒤 1280×720 → blobFromImage(640,360) [가로0.5 세로0.5]  = 리샘플링 1회, 등방 16:9→16:9
```
최종 배율은 우연히 같아지지만 1~3px 얇은 차선은 리샘플링을 거칠 때마다 뭉개진다.
→ `LaneCandidates.py` 의 `cv2.resize(image, (640,480))` 중간 단계를 제거한다.

**후처리 캔버스를 640×480 → 640×360 으로 옮긴다.** 모델 출력 해상도와 같아
`class_map` 리사이즈가 아예 불필요해지고 16:9 라 왜곡이 없다. 대신 픽셀 단위
상수를 다시 맞춰야 한다 (ROI 사다리꼴, `MIN_LANE_Y_SPAN`, `ANCHOR_ROWS`,
`MERGE_MAX_RESIDUAL` 등 — y 관련은 ×0.75). 어차피 후처리 절반이 모델로 대체되며
삭제되므로 지금이 손대기 좋은 시점이다.

> **학습 전처리 = 추론 전처리.** 어긋나면 검증 성능은 좋은데 실주행에서 무너진다.

**출력 — 헤드 두 개 유지, `ll` 의 채널 수만 변경.** 둘 다 softmax 이전 logit.

| 출력 | 지금 | 바뀐 뒤 | 의미 |
|---|---|---|---|
| `da` | (1, 2, 360, 640) | **그대로 유지** | 주행가능영역 |
| `ll` | (1, 2, 360, 640) | (1, **6**, 360, 640) | 차선 → 차선 **종류** |

**디코딩 변경** (`_run_segmentation()` 안):
```python
# 지금
mask = (logits[0, 1] > logits[0, 0]).astype(np.uint8) * 255

# 바뀐 뒤
class_map = np.argmax(logits[0], axis=0).astype(np.uint8)      # 0~5
```

**후단이 받는 것**:
```
class_map (640×360, 0~5)
  ├─ 후보 추출용 마스크 = np.isin(class_map, [1,2,3])   ← 기존 이진 마스크 자리
  ├─ 후보별 종류        = 후보 픽셀들의 최빈 클래스 → dashed = (클래스 == 2)
  ├─ 정지선             = (class_map == 4)   ← 수평 성분 휴리스틱 폐기
  └─ 유도선             = (class_map == 5)   ← 차선 후보에서 제외
```

**ONNX 그래프에서 실제 변경점은 `ll` 헤드 마지막 conv 의 출력 채널 2→6 하나뿐이다.**
백본·`da` 헤드·입력 크기·연산자 종류가 동일해 cv2.dnn 호환성(177ms / 5.6 FPS)이
유지된다.

**`da` 를 유지하는 이유**: `ll` 이 6클래스로 믿을 만해지면 `combine_masks` 의 HSV
폴백은 필요 없어져 `da` 의 역할이 줄어든다. 하지만 백본을 공유하므로 **유지 비용이
사실상 0** 이고 자유공간·경로 생성에 쓸모가 있다. 지워도 얻는 게 없다.

**주의**: 얇은 차선(1~3px)에 6채널 argmax 를 걸면 한 차선 안에서도 픽셀마다 클래스가
흔들린다. 픽셀 단위로 쓰지 말고 **후보 단위 최빈값**으로 확정한다. 기존 조각 병합·
트랙 연관 로직을 유지해야 하는 이유이기도 하다.

#### 학습

**기존 `lane_segmentation.onnx` 의 `ll` 헤드를 6채널로 교체하고 파인튜닝.**

이유:
- 입력 크기·백본·출력 구조가 그대로라 **cv2.dnn 로 계속 로드된다**
  (`CLAUDE.md` 측정: cv2.dnn 177ms vs onnxruntime 337ms — 이 이점을 유지)
- 통합 비용이 디코딩 한 줄
- 백본이 이미 차선 특징을 학습한 상태라 소량 데이터로도 수렴

**학습 환경**: 로컬 MX150(2GB)에서 샘플 100장·수 에폭으로 **코드가 도는지만 확인**한
뒤, 본 학습은 **Kaggle T4(16GB, 주 30시간)** 에서 돌린다. MX150 2GB 로는 360×640
배치 1장도 빠듯해 해상도를 낮춰야 하는데, 얇은 차선에서 해상도 감소는 치명적이다.

```
로컬(CPU)      라벨 생성 — GPU 불필요
   ↓ 데이터셋 zip 업로드
Kaggle(T4)     학습 → .onnx 내보내기
   ↓ 다운로드 (몇 MB)
로컬(CPU)      cv2.dnn 추론 — 지금과 완전히 동일
```

**학습 설정**
- 손실: 클래스 가중 CrossEntropy (`ignore_index=255`). 차선 픽셀은 전체의 1% 미만이라
  **배경 가중치를 낮추지 않으면 전부 배경으로 수렴한다.**
- 증강: 밝기/대비/노이즈만. **좌우 반전 금지** — 중앙선의 좌/우 의미가 뒤집힌다.
- 체크포인트를 매 에폭 저장 (무료 GPU 세션은 끊긴다)
- ONNX export 후 **cv2.dnn 으로 로드되는지 즉시 확인** (opset 11~12 권장)

**2단계 추가 학습**: 연구실 데이터가 생기면 **새 데이터만으로 이어 학습하지 말 것**
(catastrophic forgetting). drive6 + 신규를 **합쳐서** 1단계 가중치에서 재학습한다.
데이터가 작아 비용이 싸다.

---

### Phase 4 — 통합

`src/perception/camera_perception/LaneCandidates.py` 수정:
- `_run_segmentation()`: `ll` 을 6채널 argmax → 클래스 맵 반환
- `lane_candidates()`: 후보의 `dashed` 를 **모델 클래스에서 직접** 채운다
- **삭제 대상**: `_probe_anchor`, `_track_verdict`, `DASH_*` 상수, `fill_ratio` 판정
  — 모델이 대체한다
- **유지**: 트랙 ID 연관, `coasted`(급커브 보완), 합동 피팅 병합 — 종류 판별과
  무관하게 여전히 유용하다
- 정지선은 `last_horizontals` 휴리스틱 대신 클래스 4 픽셀로 직접 얻는다

## 6. 검증

1. **라벨 정합** (Phase 1 직후, 가장 중요): 라벨 오버레이 영상을 눈으로 확인.
   어긋나면 이후 전부 무의미.
2. **학습 지표**: 클래스별 IoU. 특히 `white_dashed` 와 `yellow` — 후처리가 실패하던 지점.
3. **실주행 비교**: `python LaneCandidates.py --source <녹화>/drive.mp4 --save out.mp4 --no-preview`
   로 렌더링해 현재 후처리 결과와 나란히 비교. 앞서 확인된 3가지(오른쪽 실선 깜빡임 /
   교차로 유도선 오분류 / 점선 누락)가 해소됐는지 본다.
4. **속도**: cv2.dnn 추론 시간이 기존 177ms 근처인지 측정. 크게 느려지면 배포 전제가 깨진다.
5. **`link_id` 교차검증**: `meta.jsonl` 의 `link_id` 가 일정한 구간에서 차선 종류 판정이
   흔들리지 않는지 확인.

## 8. 재개 지점 — 연구실에서 이 순서로

### 1) MGeo 재 export  (시뮬레이터, 먼저 해야 나머지가 진행됨)
```
surface_marking_set.json    노면 화살표·속도표시·글자
parking_space_set.json      주차구역 (지금 배경으로 학습되는 문제)
road_polygon_set.json       da 헤드용 (선택)
road_set.json               (선택)
```
정지선은 **더 이상 이 파일을 기다리지 않는다** — `lane_boundary_set.json` 의
`lane_type 530` 이 정지선으로 확인됐다.

### 2) `RecordDrive.py` 확장  ← 가장 시급. 녹화 전에 끝나야 한다
- **`ObjectInfo` 수신 추가** — `meta.jsonl` 각 줄에
  `objects: [{pose_x, pose_y, pose_z, heading, size_x, size_y, size_z, objType}]`.
  **녹화 시점에만 얻을 수 있다.** 없으면 그 데이터는 가려짐을 처리할 수 없어
  모델이 차를 뚫고 차선을 그리도록 학습된다.
- **축소 저장 제거** — `cv2.resize(image, FRAME_SIZE)` 를 없애 원본 해상도 유지.
  이걸로 "drive6 원본 해상도 미상" 미지수가 사라진다.
- **PNG 무손실 저장** — `frames/frame_000123.png` 형식. **0 채움 필수**
  (`meta.jsonl` 의 idx 와 짝을 맞추는 근거가 파일명 정렬 순서다).
- 포트는 **1101 그대로**. 시뮬레이터 Network Settings 에서 한 번만 확인.

### 3) 한 바퀴 시험 주행 → `CheckRecording.py`
본 녹화 전에 한 바퀴만 돌고 점검한다. 문제를 작은 데이터에서 잡아야 원인을 찾을 수 있다.
```
python CheckRecording.py --recording <시험녹화>
```
실효 fps / 렉 / 자차 위치 정체 / `ObjectInfo` 수신 / 해상도 / 거리 기준 예상 장수를
한 번에 찍어 준다. drive6 기준값이 같이 나오므로 비교하면 된다.

**drive6 실측 (비교 기준)**
```
2772프레임 · 5분 7초 · 2179m · 평균 26km/h · 실효 9.0 fps
프레임 간격  중앙 95ms / 최대 3408ms,  0.5초 넘는 끊김 7회 합계 11.4초(3.7%)
자차 위치 정체 17.3% (예상 오차 중앙 31cm / 최대 247cm)
```
장애물 시나리오는 여기서 더 나빠진다.

### 4) 라벨 정합 확인
```
python GenerateLabels.py --recording <시험녹화> --mgeo <MGeo> --cam-set <cam_set>     --fov-axis horizontal --detect-bonnet --frames 0,100,200,300
```
- 라벨이 도색 위에 얹히는가 — 어긋나면 이후가 전부 무의미
- 가로 편차 재측정 (drive6 에서 ~0.3m. 원인 미상, 자차 위치 정체 탓은 **아님**을 확인)
- `ignore %` 가 15% 를 넘지 않는가

### 5) 새 파일의 타입 판단 → 클래스 확정
```
python InspectMapTypes.py --recording <시험녹화> --mgeo <MGeo>     --cam-set <cam_set> --set surface_marking_set
python InspectMapTypes.py ... --set parking_space_set
```
타입마다 PNG 한 장(위 측정값, 아래 화면 4장, 초록=그 타입)이 나온다.
**보고 직접 정한다.** 숫자만으로 추측하지 말 것 — `530` 을 정지선이 아니라고
오판했던 게 그렇게 나온 실수다. 확정 못 하는 도색은 `unknown`.

### 6) 본 녹화 — 8바퀴

모든 축을 교차시키면 24바퀴지만, 축마다 골고루 덮이기만 하면 8바퀴로 충분하다.
**시간대는 11시·15시만 쓴다** — 그림자 방향의 양 극단이라 13시는 그 사이로
보간된다. 반면 `sunny ↔ foggy` 는 보간이 안 되는 별개 외형이라 둘 다 필요하다.

| # | 날씨 | 시간 | 차로 | 장애물 |
|---|---|---|---|---|
| 1 | sunny | 11시 | 1차로 | **있음** |
| 2 | sunny | 11시 | 2차로 | 없음 |
| 3 | sunny | 15시 | 1차로 | **있음** |
| 4 | sunny | 15시 | 2차로 | **있음** |
| 5 | foggy | 11시 | 1차로 | 없음 |
| 6 | foggy | 11시 | 2차로 | **있음** |
| 7 | foggy | 15시 | 1차로 | **있음** |
| 8 | foggy | 15시 | 2차로 | 없음 |

각 축이 4:4 로 균형이고 장애물은 5/8(63%). **장애물을 한 조건에 몰지 말 것** —
몰리면 모델이 "안개면 차가 있다" 같은 엉뚱한 상관을 배운다.

한 바퀴 2179m / 5분이므로 8바퀴 = 약 40분 주행 (렉이 있으면 더 걸린다).

#### PNG 는 프레임 수가 아니라 **이동 거리** 기준으로 저장한다

렉이 오면 fps 가 흔들려 "N프레임마다"가 무너진다 (9fps 에서 6프레임=4.7m 인데
4fps 로 떨어지면 10m 이상). 거리 기준이면 렉과 무관하고, 계획이 원하던
"`pos_x/pos_y` 기준 구간 균등 샘플링"이 저절로 되며, 정차 중에 같은 그림이
쌓이는 것도 막힌다.

| 간격 | 1바퀴 | 8바퀴 |
|---|---|---|
| 3m | 726장 | 5,808장 |
| **4m** | **544장** | **4,352장** |
| 5m | 435장 | 3,480장 |

**4m 권장.** 앞서 잰 희소 클래스 빈도(crosswalk 17%, stopline 29%)로 환산하면
4,352장에서 crosswalk 740장 / stopline 1,262장이라 충분하다.

## 9. 열린 항목 / 나중으로 미룬 것

**열린 항목**
- `surface_marking_set.json` (K-City) 확보 가능 여부 — MORAI 재 export 필요
- drive6 의 원본 해상도 — 재녹화로 해결
- 지도-도색 가로 편차 ~0.3m 의 정체 — 지도 정합은 아님(sin/cos 설명력 1%), 자차 기준 오차로 보이나 산포가 커서 drive6 로는 확정 불가

**나중으로 미룬 것**
- **ego 좌/우 차선 헤드** — `link_id` 로 자차 차로를 알고 lane_boundary 가 링크에
  연결되므로 "이 경계가 자차의 왼쪽"을 자동 라벨링할 수 있다. `CLAUDE.md` 가 기록한
  쌍 선택 실패(검출률 70%→64%)를 모델이 대체할 수 있어 매력적이지만, **1차에 섞지
  않는다.** ego 상대 클래스는 시점 의존이라 더 어렵고, 섞으면 실패 시 "종류 판별이
  안 된 건지 ego 판정이 안 된 건지" 구분이 안 된다. 나중에 **별도 3채널 헤드**
  (bg / ego_left / ego_right)로 추가한다.
- **측면 카메라(ID2/ID3) 활용** — 차선 인식용이 아니라 차선변경 사각지대·cut-in
  감지용. 쓰려면 별도 모델이 필요하고 우선순위는 낮다.
